Business logic · Technical logic · User logic · Action checklist

⚡

Overall: Strong plan with one critical risk

The strategy is well-conceived, the cold-start solution is clever, and the MVP scope is tight. The single biggest risk is geocoding accuracy — a map full of pins in the wrong location is worse than an empty map. Everything else is fixable. Do not start building the app until the pipeline is confirmed to be producing accurate data.

Action Checklist

0 / 9 done
Add Google Geocoding API key to .env Critical

The pipeline code already supports it — it's just not configured. Without it, many pins will land in the wrong place. Get a key from Google Cloud Console, add GOOGLE_GEOCODING_API_KEY=AIza... to .env.

Run the pipeline once and verify data in Firestore Critical

Run npm run dev -- --once, then open the Firestore console. Confirm at least 5 reports exist with correct Lagos coordinates before touching the app. If coords look wrong, the geocoding key is the first fix.

Add Firestore composite indexes Critical

The app's map and feed queries filter on multiple fields (isActive + timestamp, isActive + location.area + timestamp). Without composite indexes these queries will fail or time out at scale. Set them up in the Firebase console before beta.

Decide and document the push notification geofencing approach High

"Flood reported 0.8km from you" is a killer feature but Firestore has no native geospatial queries. You need a concrete plan before Week 3: geohashing, a Cloud Function with Distance Matrix API, or a third-party service. Don't discover this mid-build.

Expand the hardcoded Lagos areas fallback list High

Currently only 28 areas are hardcoded in src/processors/parseReport.ts. Expand to 80–100 key Lagos areas as a geocoding fallback. This is cheap insurance while the Geocoding API key is being set up. One afternoon of work.

Fix or remove the broken Claude integration High

src/lib/anthropic.ts is empty and parseReport-claude.ts calls functions that don't exist. The keyword parser works fine for MVP — either delete the Claude files to avoid confusion, or properly implement the Anthropic SDK integration. Don't leave broken code that looks like a working upgrade path.

Define the auth strategy (anonymous vs phone OTP) High

The plan lists this as an open question. Decide before building any screen that touches auth. Recommendation: anonymous first with optional phone upgrade — lowest friction for Lagos users, preserves leaderboard integrity later.

Name 3 specific B2B targets for Phase 4 sponsorships Medium

"Logistics companies sponsor leaderboards" needs to become a named list (e.g. Kwik, Gokada, DHL Nigeria) with a first-contact plan. Don't wait until Week 4 to think about this — early conversations inform product decisions.

Remove unused axios and zod from package.json Low

Both are listed as dependencies but never imported anywhere in the codebase. The pipeline uses native fetch() and manual validation instead. Remove them to keep the install clean and dependencies honest.

Detailed breakdown

📈 Business Logic
Sound

What's right

  • Cold-start via RSS pipeline is the correct answer to the empty map problem. Every location app dies on Day 1 without data.
  • WhatsApp bridge (Phase 2) is genuinely smart for Lagos. Users already share traffic in WhatsApp groups — this meets them where they are and removes the app install barrier entirely.
  • Recruiting 20–30 power riders beats passive user growth for a content network. Correct instinct.
  • Points without cash-per-report is the right anti-spam design. Paying per submission would tank data quality immediately.
  • Hyper-focus on Lagos for MVP is correct. Do not expand until the Lekki corridor is provably alive.

What needs revisiting

  • B2B monetisation is underdeveloped. "Logistics companies sponsor leaderboards" needs named targets and a first-contact plan before Week 4, not after.
  • No Waze answer. The plan correctly says "we don't compete with routing" but doesn't give a one-line reason for why a user opens Voxiro instead of Waze for local awareness. You need that answer before acquisition starts.
  • Google Maps API billing has no cost estimate in the plan. At 50k MAU the Maps SDK bill becomes significant. Worth a napkin-math check before launch.
⚙️ Technical Logic
Mostly Sound — 2 Issues

What's built well (from code inspection)

  • Clean TypeScript architecture: scrapers → processors → services. Well separated, easy to extend.
  • Keyword parser is MVP-appropriate. No API costs, works on day one, good enough for cold-start.
  • Deduplication logic is correct — 1-hour window, same type + area prevents duplicate spam.
  • Cron scheduling (30min scrape + 15min expiry) matches the product requirements exactly.
  • Stack choice (Firebase + React Native + Expo) is right for this context: real-time listeners, no DevOps, one codebase for Android and iOS.
🚨 Issue 1 — Geocoding accuracy is the top risk and it's not solved. The pipeline has 28 hardcoded Lagos areas. Lagos has hundreds of named locations. Incidents not matching those 28 get an approximate coordinate or are dropped entirely. A pin placed 2km from the actual incident destroys trust faster than no pin at all. The Google Geocoding API key is already supported in the code — it just hasn't been configured.
⚠️ Issue 2 — The Claude integration is a broken skeleton. anthropic.ts is empty and parseReport-claude.ts calls functions that don't exist. The plan presents Claude as a clean upgrade path — in reality, enabling it would crash the pipeline immediately. Either clean it up or delete it, but don't leave it as-is.

Other gaps (minor)

  • No Firestore composite indexes are defined. The queries in the plan (isActive + timestamp, isActive + location.area + timestamp) will be slow or fail without them.
  • The LASMA scraper file exists but returns an empty array. It's a placeholder — fine to leave, but don't count it as a live data source.
  • axios and zod are in package.json but never imported anywhere. The code uses native fetch() instead.
👤 User Logic
Strong — 1 Gap

What's right

  • 3-tap report flow is the correct constraint. Do not let scope creep add a fourth step.
  • Auto-detected location removes the single biggest UX friction point. Never make users type an address.
  • Relative timestamps ("5 mins ago") are correct. Absolute timestamps kill trust perception for incident reports.
  • "All clear in your area" empty state is the right call. A blank map with no context reads as broken.
  • Offline awareness (show last known state on 3G drop) is noted in the plan. This must be explicitly handled in the app code, not just documented.
  • Points tier names (Area Scout, Road Commander, Voxiro Legend) are Lagos-appropriate without being forced.
⚠️ Gap — Push notifications require geofencing, and that's non-trivial. "Flood reported 0.8km from you" is the killer feature but Firestore has no native geospatial query support. Week 3 lists this as a task but gives no implementation path. This needs a concrete approach decided before Week 3 starts — geohashing, a Cloud Function, or a third-party service. Don't discover this mid-build.

One watch item

  • The confirmation system (tap → +1 count, slightly larger pin) has no abuse prevention for MVP. This is acceptable to defer, but add a Week 4 revisit to check confirmation abuse once real data exists.
